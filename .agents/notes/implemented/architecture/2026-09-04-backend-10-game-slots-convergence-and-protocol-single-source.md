# Agent Note: Backend 10-Game Slots Convergence and Protocol Single Source

Status: implemented

## Problem
在语言服务器核心调度（`src/Main/Program.fs`）与前后端协议层中，存在明显的结构冗余与维护割裂：
1. **10 款游戏槽位代码高度重复**：对 Stellaris、CK2/3、EU4、HOI4、VIC2/3、IR 等 10 款 Paradox 游戏的状态槽位、事件监听与加载分支大量采用模板化复制粘贴，代码急剧膨胀。
2. **活跃请求与缓存键空间分散**：各个命令处理逻辑分散维护请求状态与缓存索引，缺乏全局统一的请求生命周期跟踪。
3. **协议与命令跨层维护脱节**：前端 VS Code 扩展端与 F# 后端 LSP 间的自定义命令集合（`cwtools.ai.*`）及传输契约未建立单一事实来源，手工维护极易发生字段名称或枚举漂移。
4. **协议序列化退化风险**：LSP 响应序列化（如 `writeTextDocumentSyncKind`）曾因格式匹配异常影响客户端握手。

## Decision
1. **收敛 10 款游戏槽位为统一结构模型**：
   - 将针对各具体游戏的同构逻辑抽象为通用的游戏槽位调度模型，以统一的 `GameType` 驱动生命周期、变更通知与缓存管理。
2. **统一活跃请求生命周期与缓存命名空间**：
   - 建立集中的请求上下文追踪器，规范化各子系统缓存 Key 的生成与失效逻辑。
3. **确立跨层协议单一事实来源**：
   - 统一定义 LSP 自定义命令与通信契约，使得 TypeScript 侧的调用与 F# 侧的模式匹配严格保持契约对齐。
4. **修复协议序列化并加固测试退出门禁**：
   - 恢复 `writeTextDocumentSyncKind` 的标准序列化输出；在测试 Harness 执行失败时强制退出码为 1。

## Alternatives considered
- **为每款游戏独立拆分独立的 Program 文件**：
  - *未采纳原因*：各游戏的核心流程完全一致（读取规则、解析脚本、构建 AST、发布诊断），拆分文件只会制造更多的重复胶水代码；收缩为参数化槽位是最佳的架构解。
- **通过 JSON 弱类型字典接收所有 LSP 命令参数**：
  - *未采纳原因*：牺牲了 F# 的静态类型安全，且容易在运行时出现不可预测的键名错误；维持强类型单源契约能最大化保障跨进程可靠性。

## Consequences
- `Program.fs` 的样板代码大幅消减，维护负担减半。
- 彻底消除了协议层命令字面量漂移与序列化不合规隐患。
- 使得新增或调整游戏规则逻辑时的变动面收拢至最小。
