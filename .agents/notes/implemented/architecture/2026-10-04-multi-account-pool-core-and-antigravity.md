# Agent Note: 多账号号池内核与 Antigravity 接入

Status: implemented

## Problem

订阅线路此前都是**单账号**：一个凭据槽位、一个账号。这带来三个具体限制：

1. **无法轮转**：一个账号撞到 429 时，唯一的结果是整轮请求失败；
2. **无法分流**：想同时用两个账号（例如一份已耗尽、一份还有额度）只能手工来回登录；
3. **凭据失效即整条线路不可用**：一个被撤销的令牌会让用户以为需要重新登录，
   而其实另一个账号仍然可用。

参照实现为每条线路各写了一份号池（`common/account-pool.ts` 925 行 + 各线路适配器）。
本仓库此前没有任何号池抽象。

## Decision

### 新增 provider 无关的内核 `client/extension/ai/pool/accountPool.ts`

存储、序列化、可调度性、轮转与冷却规则都在内核里；各线路只提供少数钩子（去重键、别名、
续期、失败分类）。这是**有意的**：

> 顺序耗尽 / 轮询 / 粘性、429 冷却换号、账号级失效保留这几条规则一旦各写一遍就会各自
> 漂移，而它们是**路由正确性**而不是展示细节。

四条承重语义：

- **调度策略只从「已经可调度」的集合里挑**：正在冷却的账号不会被策略选中。策略描述的
  是偏好而不是越权——一个粘性偏好的账号冷却时必须退化为自动选择，而不是让整轮失败；
- **粘性保护上游前缀缓存**：多轮对话默认落在同一个账号上。每轮换号会让整段前缀缓存
  失效，这是「多账号」最容易引入的性能退化；
- **凭据失效保留账号行**：401/403 让该账号退出轮转但**不删除**。重新登录会原地恢复它，
  而删掉会让用户丢掉一个仍然有效的套餐；
- **冷却过期即视为不存在**：对外汇报时已过期的冷却不会被报成「仍在冷却」。

并发安全靠一条**写队列**：所有变更在队列里串行读改写，因此两个同时到达的登录不会各自
通过一个对方已经作废的检查（容量、去重、主账号判定都基于实时文档）。

两处实现细节是缺陷修复而非设计选择：

- **单飞续期**（`refreshInFlight`）：并发调用者必须**共用**一次轮换，而不是各自花掉同一枚
  refresh token。上游会作废已轮换的令牌，所以除第一个之外全部被拒——一次突发流量就让
  账号看起来被撤销了。这是接入 Antigravity 时**实测暴露**出来的（并发测试期望 1 次
  续期，实际发生 2 次）；
- **`AccountPoolStore` 返回 `Thenable` 而不是 `Promise`**：VS Code 的 `SecretStorage`
  正是这样声明的，收窄成 `Promise` 会让真实实现无法传入。

### 新增 `client/extension/ai/antigravity/accountPool.ts`

Antigravity 自己的可变行为：

- **身份键不是令牌**：Google 的 access/refresh token 每次轮换都会变，用令牌做键会在每次
  续期后把同一账号看成新账号并产生幽灵行。身份取凭据里的 email（同一个人重登即同一
  账号），没有 email 时回落到 `recordKey`（同一次登录会话的稳定标识）；
- **失败分类只认 401/403**：网络抖动与 5xx 必须让账号留在原地，否则一次临时故障就会
  让用户以为需要重新登录；
- **旧单凭据被投影为主账号**：升级不再是「什么都没了」；主账号同时镜像回单凭据槽位，
  让仍然读旧槽位的路径继续工作。

### 接入 `antigravity/oauthService.ts` 与请求路径

- `getRequestContext` 改为从号池取账号，并返回该账号的 `accountId`；
- **项目缓存按账号隔离**：原先是一个不带键的缓存。轮转之后它会把手前一个账号的 project
  交给下一个账号，而那是服务端会拒绝的请求。实测暴露：缓存必须随账号失效；
- **登录加入号池**：一次完成的登录会把账号并入池子，去重键让重复登录变成原地重新授权；
- **登出清空整池**：只删单凭据槽位会把刚被移除的凭据留在池里继续发请求；
- **续期绑定会话信号**：登出会中止进行中的轮换，而不是让它跑完再把凭据写回来；
- **429 换号**：`callAntigravity` 维护本次请求已尝试的账号集合，429 冷却当前账号后换一个
  重试，401 强制续期一次再重放同一请求体。上限 3 次尝试；
- **会话变更优先报错**：登出期间号池会报「账号在续期中消失」，但那不是可操作的原因——
  `getRequestContext` 会把它翻译成 `session changed`。这也是实测暴露的：原测试断言的是
  `/abort|session/`。

### 回归测试

新增 `client/test/unit/accountPool.test.ts`（27 例）：去重原地更新、容量上限、删除主账号后
的补位、损坏文档按空池处理、旧单凭据投影、三种策略的行为（含轮询摊满整池、粘性保持同一
账号）、**冷却账号绝不被选中**、排除已尝试账号、冷却过期不汇报、冷却下限夹取、冷却不删号、
失效账号留行且可清除、全不可用时报 429 与最短等待、过期即续期并落盘、**并发续期单飞**、
有效凭据不续期、临时失败原样上抛、分类为终局时停用账号、Antigravity 身份键与失败分类、
SecretStorage 文本的解析、坏行跳过、策略回落、端到端存取、**摘要绝不含凭据**。

`antigravity.test.ts` 的并发用例断言更新为新契约（返回值包含 `accountId`）。

## Alternatives considered

1. **每条线路各写一份号池**（参照实现的做法）：否决。这些规则是路由正确性，重复实现必然
   漂移；内核 + 少量钩子把差异收敛到真正因线路而异的部分。
2. **用令牌做账号身份键**：否决。令牌每次轮换都变，会产生幽灵账号。
3. **给每条线路都接号池**：本轮只做 Antigravity（计划里的起点）。内核是通用的，其它线路
   接入是后续工作；先把内核与一个真实接入点验证透，好过同时铺开四个半成品。
4. **冷却时长照抄上游**：否决。没有 `Retry-After` 时需要兜底值，且需要一个下限避免一次
   抖动就把账号永久排除。
5. **失效账号直接删除**：否决。用户会丢掉一个仍然有效的套餐，且重新登录无法恢复那一行。
6. **键不与账号绑定的项目缓存**：否决（实测暴露）。轮转后会把前一个账号的 project 发给
   下一个账号，服务端拒绝。
7. **并发时各调各的续期**：否决（实测暴露）。除第一个之外全部拿到作废令牌，一次突发就让
   账号看起来被撤销。

## Consequences

- Antigravity 支持多账号：顺序耗尽 / 轮询 / 粘性三种调度、429 冷却换号、账号级失效保留、
  设为主账号与清除冷却；
- 单凭据槽位仍是主账号的镜像，所有既有读取路径不受影响；升级不会丢账号；
- 并发请求共享一次续期，不再有「突发流量把账号打成失效」的问题；
- 摘要只含非凭据信息（别名、主账号标记、冷却、失效状态），卡片拿不到凭据材料；
- 内核是 provider 无关的，其它订阅线路接入只需提供自己的钩子；
- **设置面已交付**：Antigravity 卡片新增调度策略选择器与账号列表（主账号标记、冷却倒计时、
  失效提示，以及「设为主账号」/「清除冷却」按钮）。协议链为
  `setAntigravityPoolStrategy` / `setAntigravityPrimary` / `clearAntigravityCooldown`，
  视图经 `settingsData.antigravityAccount.pool` 下发并在边界上由
  `isAntigravityAccountStatus` 校验（含 `pool` 形状）。
- **全部线路已接入**（后续同一变更内完成）：新增 `pool/oauthAccountPool.ts` 通用工厂 +
  `pool/subscriptionPools.ts` 各线路规格 + `pool/poolRegistry.ts` 注册表；Antigravity 也改为
  复用该工厂。codex-chatgpt、kimi-code-plan、workbuddy-subscription、minimax-code、
  claude-subscription、commandcode（静态 Key）全部纳入同一套轮转、冷却与失效保留规则。
  细节见 `.agents/notes/implemented/architecture/2026-10-04-subscription-pool-all-lines.md`。
